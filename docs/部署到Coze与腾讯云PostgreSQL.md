# 部署到 Coze + 腾讯云 PostgreSQL

> 整理内容：服务部署方案、多系统共用实例如何建库，以及数据库 / 文件存储价格参考。

***

## 一、方案说明：服务部署到 Coze，数据库买腾讯云 PostgreSQL

这个方案 **可以**：**应用跑在扣子（Coze），业务库用腾讯云 PostgreSQL**。注意把「数据库」和「文件存储」分开。

### 1.1 推荐架构

```
用户浏览器
    ↓
扣子编程部署的 Next.js CRM（公网域名 *.coze.site 等）
    ↓
腾讯云 PostgreSQL（客户、商机、账号……）
    ↓（文件上传另走）
Coze Storage 或 腾讯云 COS（录音、知识库文件）
```


| 部分       | 放哪                        | 说明              |
| -------- | ------------------------- | --------------- |
| 网站 / API | **扣子（Coze）部署**            | 管网站和 API        |
| 业务表数据    | **腾讯云 PostgreSQL**        | 客户、商机、账号等       |
| 上传文件     | **Coze Storage 或腾讯云 COS** | 录音、知识库；不要写容器本地盘 |

### 1.2 腾讯云 PostgreSQL 怎么买才接得上

| 项         | 建议                                         |
| --------- | ------------------------------------------ |
| 产品        | 云数据库 PostgreSQL（版本 14/15/16 均可，本地开发常用 16）  |
| 地域        | 选常用地域即可                                    |
| **公网访问**  | **必须开**（扣子一般连不上仅内网地址）                      |
| 安全组 / 白名单 | 先可临时 `0.0.0.0/0` 测通，再收紧；若有扣子出口 IP 再按 IP 放行 |
| SSL       | 云库通常要求，连接串加 `?sslmode=require`             |
| 库名        | 例如建库 `sales_crm`，业务用户单独建、权限收紧              |

连接串示例：

```text
DATABASE_URL=postgresql://用户名:密码@公网地址:5432/sales_crm?sslmode=require
```


本地用这个串跑一次初始化（确认连的是腾讯云库，不是本机）：

```bat
npm run db:init
```


### 1.3 在扣子部署时要配的环境变量

生产环境至少：

| 变量                    | 作用                  |
| --------------------- | ------------------- |
| `DATABASE_URL`        | 腾讯云 PG 连接串          |
| `SESSION_SECRET`      | 登录会话密钥（随机长串）        |
| `COZE_AI_API_KEY` 等   | AI（若用）              |
| `COZE_STORAGE_*`      | 文件存储（见下）            |
| `PUBLIC_APP_BASE_URL` | 扣子给的公网网址（转写/回调等会用到） |

扣子若提示「内置数据库同步」，**使用外购 PG 时不要依赖那套同步**；以自己的 `DATABASE_URL` 为准。

### 1.4 「存储」别和数据库搞混

| 类型          | 放哪                        | 说明                                              |
| ----------- | ------------------------- | ----------------------------------------------- |
| 业务表数据       | **腾讯云 PostgreSQL**        | 本方案核心                                           |
| 上传的录音/知识库文件 | **Coze Storage 或腾讯云 COS** | 配 `COZE_STORAGE_URL/AK/SK/BUCKET`（COS 也可 S3 兼容） |
| 不配对象存储      | 会写到容器本地 `storage/`        | **上线后不可靠，会丢**                                   |

### 1.5 和「CloudBase 云托管」对比

| <br /> | 扣子部署 + 腾讯云 PG | CloudBase 云托管 + 腾讯云 PG |
| ------ | ------------- | ---------------------- |
| 应用在哪   | 扣子            | 腾讯云云托管                 |
| 数据库    | 都可以是腾讯云 PG    | 同左                     |
| 公网域名   | 扣子分配 / 自定义    | 云托管域名                  |
| 企微回调   | 用扣子 HTTPS 域名  | 用云托管 HTTPS 域名          |
| 运维感    | 更偏扣子编程发布流     | 更偏容器/云托管               |

两边都能外挂同一套腾讯云 PG；差别主要在 **应用跑哪、域名和发布流程**。

### 1.6 落地顺序（建议）

1. 腾讯云开通 PG，开公网，建库 `sales_crm`
2. 本地用 `DATABASE_URL` 连上去，执行 `npm run db:init`
3. 代码导入/同步到扣子编程项目
4. 部署页填生产环境变量（尤其 `DATABASE_URL`、`SESSION_SECRET`）
5. 配好 `COZE_STORAGE_*`（或 COS）
6. 打开扣子域名，用演示账号登录验证
7. （以后）企微回调填这个 HTTPS 地址

### 1.7 需要提前知道的风险

1. **白名单**：扣子出口 IP 若不固定，安全组可能只能先放宽再收紧
2. **扣子对 Next 全栈的限制**：构建命令、端口、长连接/超时以扣子「部署网页应用」实际能力为准；大文件上传、长 AI 请求要实测
3. **不要**把 `.env.local` 里的密码提交进 Git

### 1.8 小结

「服务部署到 Coze + 腾讯云买 PostgreSQL」合理；再补上 **对象存储**，上线才完整。

## 二、多系统共用：腾讯云 PostgreSQL 可以建不同数据库吗？

**可以。** 腾讯云买的是一台（或一个实例）**PostgreSQL 服务**，上面可以建多个**数据库**，不同系统各用一个库即可。

### 2.1 常见拆法

```
腾讯云 PostgreSQL 实例（一份钱、一套机器）
 ├── sales_crm      ← 凯艺销售 CRM
 ├── 另一个系统库
 └── 再一个系统库
```


每个库里的表、用户数据互不影响。连接串只是库名不同，例如：

```text
postgresql://用户:密码@公网地址:5432/sales_crm?sslmode=require
postgresql://用户:密码@公网地址:5432/另一系统库名?sslmode=require
```


### 2.2 三种隔离程度（按需求选）

| 方式                               | 隔离程度          | 适用                 |
| -------------------------------- | ------------- | ------------------ |
| **同一实例、多个 database**             | 中（库与库分开，资源共用） | 多系统、想省钱 —— **最常用** |
| 同一库、不同 schema（如 `crm.` / `erp.`） | 较弱            | 强相关子系统             |
| **多个实例** 各买一份                    | 最强（资源、故障都隔离）  | 系统很重要或合规要求高        |

「几个系统都要存」时，一般 **一个实例 + 多个数据库** 就够。

### 2.3 权限建议（多系统同实例时）

* 不要所有系统共用一个超级用户

* 最好：**每个系统一个数据库用户，只授权自己的库**

  * 用户 `crm_app` → 只能连 `sales_crm`

  * 用户 `other_app` → 只能连另一个库

避免 A 系统误改 B 系统的表。

### 2.4 注意点

1. **CPU/内存/连接数是整实例共享的** —— 一个系统把连接打满，别的系统也会受影响
2. **备份一般是整实例一起备** —— 恢复时要小心别覆盖错库（可按库做逻辑备份）
3. 控制台里通常在「数据库管理」里 **新建数据库**；也可用 SQL：`CREATE DATABASE sales_crm;`

### 2.5 小结

可以、也推荐「一台腾讯云 PG + 多个数据库」；CRM 用 `sales_crm`，其它系统再建各自的库名即可。

## 三、价格参考（数据库 + 文件存储）

> **说明：** 以下为腾讯云公开文档中的**刊例价参考**（整理时点约 2026-07），实际成交价以[控制台购买页](https://buy.cloud.tencent.com/price/pgsql) / [价格计算器](https://buy.cloud.tencent.com/price)为准，常有新客折扣、资源包优惠。地域不同价格可能不同。

### 3.1 数据库：腾讯云 PostgreSQL

**计费构成（官方）：**

```text
总费用 ≈ 规格费用 + 存储（硬盘）费用 + 备份超赠送部分
         + 日志（目前超赠送部分免费）+ 公网流量（目前免费）
```

| 计费模式 | 适合 | 说明 |
|----------|------|------|
| **包年包月** | 长期稳定跑 | 一般更便宜，买得越久折扣越多 |
| **按量计费** | 短期试跑 | 用完可释放；按使用时长分三档阶梯价（越用越久单价越低） |

**官方示例（广州地域，传统云数据库 PostgreSQL）：**

| 场景 | 规格 | 费用怎么算 | 约合 |
|------|------|------------|------|
| 包年包月 1 个月 | 16 核 32 GiB + 硬盘 500GB | 规格 4096 元/月 + 硬盘 `500 × 0.72` 元/GB/月 | **约 4456 元/月** |
| 按量用 400 小时 | 同上规格 | 分三阶梯：约 11.377 / 8.533 / 5.688 元/小时 + 硬盘 0.001 元/GB/小时 | **约 3772 元**（400 小时合计） |

可见：**大规格很贵**。CRM 初期一般选**小规格**即可。

**更适合起步的规格思路（需在购买页看实时价）：**

| 建议档位 | 大致用途 | 价格怎么估 |
|----------|----------|------------|
| 小规格主实例（如 1～2 核、2～4GB）+ 硬盘 20～50GB | 单 CRM / 少量系统同实例多库 | 以购买页为准；硬盘可参考刊例约 **0.72 元/GB/月**（广州示例） |
| [TDSQL-C PostgreSQL](https://cloud.tencent.com/document/product/1556/68612) 计算节点 | 弹性、计算与存储分离 | 官方示例（广州/上海/北京）：**1 核 2GB ≈ 163.20 元/月**；另加存储按量（文档示例约 0.00486 元/GiB/小时） |

| 组合 | 粗算月费 |

| TDSQL-C 1核2GB + 约 20GB 存储 | 大约 **200 元/月上下**（163 + 存储） |
| 传统 PG 小规格 + 50GB 盘 | 往往 **一两百～数百元/月**（强依赖购买页规格与折扣） |

**多系统共用一台实例：** 只付 **一份** 实例费；建多个 database **一般不再按「库的个数」加收规格费**（仍共用 CPU/内存/连接数）。

### 3.3 Coze Storage

扣子侧对象存储（本项目环境变量 `COZE_STORAGE_*`）的计费通常跟 **扣子/Coze 套餐或资源配额** 走，**没有像腾讯云 COS 那样统一的「元/GB」公开价目表**。

- 若部署在扣子且平台赠送/包含存储额度：优先用平台说明里的额度  
- 若要**费用透明、多系统共用桶策略清晰**：直接买 **腾讯云 COS**，把 `COZE_STORAGE_URL/AK/SK/BUCKET` 配成 COS 的 S3 兼容地址即可

## 四、从 Coze PostgreSQL 迁到阿里云：只改连接串可以吗？

有人说：两边都是 PostgreSQL，代码里本来就是：

```js
// 之前（Coze）
const pool = new Pool({
  connectionString: process.env.DATABASE_URL  // Coze 的数据库地址
});

// 之后（阿里云）
const pool = new Pool({
  connectionString: process.env.DATABASE_URL  // 改成阿里云的地址
});
```

只改一行环境变量，SQL 完全不用动；迁移就是导出 → 开阿里云 PG → 导入 → 改 `.env` → 部署。

### 4.1 结论：大体对——但只适用于「本来就是用连接串连 PostgreSQL」

对本项目（`pg` + `DATABASE_URL` + 手写标准 SQL）来说，**他说得基本对**：

- 改 `DATABASE_URL` 即可切换库
- 业务 SQL（如 `SELECT * FROM customers`）一般不用改
- 没有 ORM，也不存在「换 ORM 方言」的问题

仓库 schema 也是按标准 PostgreSQL 设计的，和「换阿里云 / 腾讯云 RDS PostgreSQL」兼容。

### 4.2 别和「Coze 内置数据库」搞混

| Coze 产品 | 怎么访问 | 能不能只改连接串 |
|-----------|----------|------------------|
| **Coze 提供的 PostgreSQL**（连接串） | `pg` / `DATABASE_URL` | ✅ 可以 |
| **Coze 内置数据库**（表在扣子里、走 API/工作流） | HTTP / 工作流节点 | ❌ 不行，要改程序/流程 |

「只改环境变量」成立的是 **Coze 版 PostgreSQL**，不是 **Coze 内置业务库**。

### 4.3 需要补正的细节

1. **「约 50 元/月」**  
   - 新用户基础版活动：大约两百多/年，可能更便宜  
   - 高可用正式档：往往相当于三四百元/月量级  
   「50 元/月」只是粗估，不能当报价。

2. **导出数据**  
   更稳的是用标准工具，例如 `pg_dump` 导出再导入，不要只依赖控制台点几下（大库更容易漏/乱）。

3. **不是绝对「SQL 100% 不用动」**  
   多数能直接用，但要核对：
   - PostgreSQL **大版本**是否接近（如 14→16）
   - 有没有用环境特有的 **扩展、函数**
   - 云库常要开 **SSL**、加 **IP 白名单**
   - 库名、用户名、密码、时区

4. **「代码一行不用改」**  
   应用代码通常不用改；要改的是 **环境变量 + 网络/白名单 + 导入校验**。部署到云服务器时还要保证服务器能访问 RDS（同地域、安全组）。

### 4.4 一句话

对本项目这种「`pg` + `DATABASE_URL` + 标准 SQL」：**换阿里云 PG 主要就是迁数据 + 改连接串。**  
「程序和流程要重做」说的是 **Coze 内置库 API**，不是这套 PostgreSQL 连接方式——两件事不要混。
